# Hybrid Graph 확장 구현과 성능 분석

이번 작업의 목표는 **Hybrid가 찾은 문서를 출발점으로 그래프를 따라가, 질문에 필요한 추가 근거를 함께 찾는 것**이다. 기존 Hybrid 검색 뒤에 그래프 탐색을 붙이고, 같은 질문으로 실행해 실제로 근거를 더 잘 찾는지 확인했다.

예를 들어 “기초연금을 친척이 대신 신청할 수 있는 범위”를 묻는다면 대리 신청 안내뿐 아니라 **친족의 범위를 정의한 다른 법 조항**도 필요할 수 있다. 질문과 표현이 비슷한 문서를 찾는 데서 끝내지 않고, 그 문서가 참조하는 근거까지 가져오려는 것이 이번 확장의 목적이다.

보고서는 **① 확장을 어떻게 구성했는지 → ② 실제 성능이 어떻게 달라졌는지 → ③ 실패가 어디서 발생했는지 → ④ 이를 확인하기 위해 세운 세 가설과 실험 결과 → ⑤ 다음 개선 방향** 순서로 설명한다.

## 1 왜 Hybrid에 그래프 확장을 붙였는가

기존 Hybrid는 BM25의 단어 기반 검색과 Dense의 의미 기반 검색을 결합한다. 두 방식의 장점을 함께 사용하지만, **질문에 직접 언급되지 않은 정의·위임 조항이나 다른 출처의 보충 근거**까지 항상 상위에 올려 주지는 못한다.

그래프에는 행정 서비스와 법 조항을 노드로, “이 서비스의 법적 근거”, “이 조항이 참조하는 조항” 등을 관계로 저장해 두었다. 따라서 Hybrid가 관련 자료를 하나 찾았다면, 그 자료와 연결된 노드에서 관계를 따라 추가 근거를 찾을 수 있다.

| 기존 Hybrid | 이번 Hybrid+Graph 확장 |
|---|---|
| 질문과 관련 있는 원문 조각을 검색하고 순위를 매김 | 먼저 같은 Hybrid 검색을 수행함 |
| 검색된 문서의 법적 관계를 별도로 따라가지 않음 | 검색 결과와 연결된 서비스·조항에서 그래프 탐색을 시작함 |
| Hybrid 순위의 상위 10개를 반환함 | 기존 후보와 그래프로 모은 근거를 합쳐 상위 10개를 반환함 |

여기서 **청크**는 검색을 위해 나눈 원문 조각이고, **evidence 바인딩**은 “이 청크가 어느 노드·관계의 근거인지”를 기록한 연결이다. 이 연결을 거꾸로 조회해 탐색의 시작점을 정한다. 시작점을 이후에는 **시작 노드 또는 시드(seed)**라고 부른다.

## 2 이번 확장을 어떻게 구현했는가

### 2.1 질문이 들어왔을 때의 흐름

```text
사용자 질문
  ↓
BM25 + Dense를 결합한 Hybrid 검색
  ↓
Hybrid 후보 100개 확보
  ├─ 100개는 최종 결합 후보로 보관
  └─ 상위 10개 청크의 evidence 바인딩 조회
          ↓
      연결된 서비스·법 조항에서 시작 노드 최대 5개 선택
          ↓
      법적 근거·참조 관계를 정방향으로 최대 2단계 탐색
          ↓
      시작 노드와 탐색 경로에 연결된 원문 근거 수집
          ↓
      Graph 후보를 정렬해 최대 100개 유지
          ↓
Hybrid 후보와 Graph 후보를 청크 ID로 합치고 순위 결합
  ↓
최종 10개와 출처·탐색 경로 반환
```

기존 Graph 단독 검색은 질문과 노드 명칭을 맞춰 시작점을 찾는다. 이번 확장은 **Hybrid가 먼저 찾아온 원문을 보고 시작점을 찾는다**는 점이 다르다. 그래프에 연결되지 않은 청크도 Hybrid 후보에서는 유지한다. 다만 후보에 남는 것과 최종 10개에 남는 것은 다르다.

### 2.2 설정값과 각 설정이 맡는 역할

아래 설정은 Notion의 구현안을 이어받았다. ‘역할’은 현재 코드에서 그 설정이 어떤 제한과 동작을 만드는지 설명한 것이다. **10개·5개·2-hop·100개가 최적값이라고 검증한 것은 아니다.**

| 정한 항목 | 현재 설정 | 역할과 고려한 한계 |
|---|---|---|
| 시작점으로 볼 문서 범위 | Hybrid 상위 10청크 | 상위 문서에 진입 범위를 좁힌다. 필요한 선행 조문이 36위라면 시작점 선정에서 빠질 수 있다 |
| 전체 결합용 Hybrid 후보 | 상위 100청크 유지 | 그래프 탐색과 별개로 기존 검색 후보를 보존한다 |
| 시작점으로 인정할 연결 | 서비스·조항의 안내/본문 evidence, 또는 허용된 관계의 출발 노드 evidence | 텍스트가 비슷하다는 이유만으로 연결하지 않고, 저장된 원문 바인딩으로 진입한다 |
| 시작 노드 수 | 전체 최대 5개, 한 청크당 최대 2개 | 탐색량을 제한하고 한 청크에 시작점이 전부 몰리는 것을 막는다. 같은 청크의 노드 간 선택은 아직 ID 순서다 |
| 탐색 관계 | `GROUNDED_BY`, `REFERENCES` | 서비스→법적 근거→참조 조항을 따라간다. 제출서류의 `REQUIRES`, 처리기관의 `HANDLED_BY`는 기본 탐색에서 제외된다 |
| 탐색 방향·깊이 | 정방향, 최대 2-hop | 서비스에서 근거 조항을 거쳐 참조 조항까지 도달할 수 있는 범위다 |
| 탐색량 상한 | 노드 처리 1,000회, 엣지 처리 5,000회 | 연결이 많은 곳에서 탐색량이 지나치게 커지는 것을 제한한다 |
| Graph 후보 수 | 점수순 최대 100개 | 탐색에서 나온 모든 근거를 최종 정렬에 넣지 않고 후보 수를 제한한다 |
| 최종 반환 | 상위 10개 | 기존 검색과 같은 반환 수로 비교한다 |

`GROUNDED_BY`는 **“이 서비스는 이 조항에 근거한다”**, `REFERENCES`는 **“이 조항은 저 조항을 참조한다”**는 관계다. 관계를 따라 이동하는 한 단계를 1-hop이라고 한다. 이동하지 않고 시작 노드에 붙은 evidence를 수집하는 경우는 0-hop이다.

### 2.3 후보의 순위는 어떻게 결정하는가

**Graph 안에서는** 시작점이 나온 Hybrid 순위, 질문과 청크의 Kiwi 토큰 관련도, 이동한 hop 수로 후보를 정렬한다. 구조만 보고 순위를 정하는 방식은 아니다. BM25와 Graph의 관련도 계산에는 현재 Kiwi 토큰화를 사용하고, Dense는 임베딩 모델 자체의 처리를 사용한다.

**마지막에는** 두 순위 목록을 RRF로 합친다. RRF는 서로 다른 검색 점수의 크기 대신 **몇 위에 나왔는지**를 이용하는 결합 방식이다.

```text
최종 점수 = 1 / (60 + Hybrid 순위)
          + 1 / (60 + Graph 순위)
```

한 목록에만 있는 청크는 그 목록의 점수만 받는다. 두 목록에 모두 있으면 두 점수를 받는다. BM25와 Dense를 합쳐 Hybrid를 만드는 첫 결합 뒤에, **Hybrid와 Graph를 합치는 두 번째 결합**이 있는 구조다.

<details>
<summary>정확한 Graph 점수식과 구현 파일</summary>

기본 시작점 가중치는 `1 / 시작 청크의 Hybrid 순위`다. Graph 점수는 이 가중치에 `(0.45 + Kiwi IDF 관련도) / (1 + 0.12 × hop)`을 곱하고, 조건 evidence에는 0.95를 추가로 곱한다. IDF 관련도는 질문의 토큰 중 corpus에서 드문 토큰에 더 큰 비중을 주는 겹침 점수다.

[hybrid_graph.py](../../scripts/hybrid_graph.py)가 시작점 선택·탐색·결합을 구현하고, [run_week4.py](../../scripts/run_week4.py)가 기본 확장과 가설별 조건을 실행한다. [compare_extension.py](../../scripts/compare_extension.py)는 비교 조건과 평가 결과를 확인한다.

</details>

## 3 실제로 기존 검색보다 나아졌는가

### 3.1 기본 Hybrid와 기본 확장의 결과

같은 corpus와 질문에서 **기존 Hybrid의 상위 10개**와 **확장의 상위 10개**를 비교했다. 전체 204질문 중 근거가 정해진 177질문을 평가하고, 추가 확인·응답 보류가 필요한 27질문은 진단용으로 분리했다.

질문 하나에 필요한 근거가 세 종류라면 세 종류를 모두 찾아야 **완전 회수**다. **Recall@10**은 필요한 근거 중 찾은 비율을 질문마다 계산한 평균이고, **Hit@10**은 하나라도 찾은 질문 비율, **MRR@10**은 첫 정답 근거가 얼마나 앞에 나오는지를 나타낸다. 답변 생성의 정확도를 평가한 수치는 아니다.

| 지표 | 기존 Hybrid | 기본 Hybrid+Graph | 변화 |
|---|---:|---:|---:|
| 필요한 근거를 모두 찾은 질문 | **140/177** | **132/177** | −8질문 |
| Recall@10 | 82.20% | 77.97% | -4.24%p |
| Hit@10 | 85.31% | 81.36% | -3.95%p |
| MRR@10 | 0.6061 | 0.5579 | -0.0482 |

**기본 확장은 기존 Hybrid보다 낮았다.** 필요한 근거를 모두 찾은 질문은 8개 줄었고, Recall은 4.24%p 낮아졌다. 근거 회수량이 늘어난 질문은 9개였지만 줄어든 질문은 15개였으며, 회수 개수는 같고 근거 종류가 바뀐 질문도 1개 있었다.

완전 성공만 보면 **새로 성공한 질문 6개보다 기존 성공을 잃은 질문 14개가 많았다.** 따라서 “그래프를 붙였으니 성능이 올랐다”고 결론 낼 수 없다.

<details>
<summary>BM25·Dense·Graph 단독을 포함한 전체 벤치마크</summary>

| 검색 방식 | 완전 회수 / 177 | Recall@10 | MRR@10 |
|---|---:|---:|---:|
| BM25 | 128 | 75.61% | 0.5358 |
| Dense | 126 | 75.52% | 0.4987 |
| 기존 Hybrid | 140 | 82.20% | 0.6061 |
| Graph 단독 0-hop | 78 | 46.80% | 0.3747 |
| Graph 단독 1-hop | 108 | 62.81% | 0.4650 |
| Graph 단독 2-hop | 105 | 61.68% | 0.4636 |
| Graph 단독 3-hop | 105 | 61.68% | 0.4636 |
| 기본 Hybrid+Graph | 132 | 77.97% | 0.5579 |

확장은 기존 Graph 단독보다 높은 성능을 보였지만, **기존 Hybrid 초과 성능**은 달성하지 못했다. 모든 행은 같은 177질문을 평가했다.

</details>

### 3.2 어떤 질문에서 좋아지고 나빠졌는가

각 칸은 **Recall@10 (완전 회수 질문 수)**다. 작은 유형의 결과를 일반적인 우월성으로 확대하지 않도록 질문 수도 함께 표시했다.

| 질문 유형 | 질문 수 | 기존 Hybrid | 기본 확장 |
|---|---:|---:|---:|
| 직접 질의 | 45 | 95.56% (43/45) | 91.11% (41/45) |
| 서비스 찾기 | 15 | 70.00% (10/15) | 80.00% (12/15) |
| 제출서류 | 19 | 89.47% (17/19) | 60.53% (10/19) |
| 요건·조건 | 78 | 80.56% (61/78) | 79.27% (61/78) |
| 법적 근거 | 4 | 62.50% (2/4) | 58.33% (2/4) |
| 법령 상호참조 | 10 | 68.33% (5/10) | 53.33% (3/10) |
| 여러 출처·다단계 | 5 | 36.67% (1/5) | 60.00% (2/5) |
| 처리기관 | 1 | 100.00% (1/1) | 100.00% (1/1) |

- **서비스 찾기와 여러 출처를 모으는 질문은 개선됐다.** 한 서비스에 묶인 여러 원문 근거를 함께 모으는 효과가 있었다.
- **제출서류 질문은 17/19→10/19로 크게 악화됐다.** 기본 탐색이 `REQUIRES` 관계를 제외한 것이 실제 사례의 원인 중 하나였다.
- **법령 상호참조도 5/10→3/10으로 낮아졌다.** 참조 조항에 도달하는 것만으로는 부족했고, 찾은 조항이 최종 순위에 남아야 했다.

**개선 사례 — [SJ-A-003](QUESTION_TRACES.md#sj-a-003):** 정부24의 유료 안내와 성남시 무인발급 무료 안내의 차이를 묻는다. Hybrid는 필요한 세 근거 중 하나만 찾았지만 확장은 세 개를 모두 찾았다. 정부24 개요는 Hybrid 84위→결합 4위, 지자체의 두 표 행은 각각 5→2위, 18→3위로 올라왔다. 세 근거의 최고점 경로는 모두 서비스의 0-hop evidence였다. **서비스에 다른 출처를 묶어 둔 연결 자체가 도움을 준 사례**이며, 여러 hop을 거친 성공으로 설명하지 않는다.

## 4 성능이 떨어진 이유는 어디에 있었는가

### 4.1 후보를 못 찾은 문제와 찾고도 밀린 문제

그래프를 붙인 뒤 **후보 전체의 Recall은 97.65%→98.02%로 소폭 올랐다.** 반면 최종 10개의 Recall은 82.20%→77.97%로 낮아졌다. 필요한 근거를 더 모으는 능력과 그 근거를 최종 선택하는 능력이 따로 움직인 것이다.

| 기본 확장에서 완전 회수하지 못한 45질문 | 질문 수 | 의미 |
|---|---:|---|
| 필요한 근거가 후보 안에 있지만 Top-10에서 누락 | **41** | 후보를 늘리는 것보다 최종 선택을 먼저 점검할 대상 |
| 필요한 근거가 후보 밖에만 있음 | 3 | 시작점·연결·탐색 범위를 점검할 대상 |
| 후보 부재와 순위 탈락이 함께 있음 | 1 | 두 단계의 문제가 섞임 |

근거 그룹 단위로는 누락된 54그룹 중 **50그룹이 후보 안에 있었다.** 평가 질문 177개는 모두 시작점이 있었고 노드·엣지 탐색 한도에 걸린 경우는 없었다. 다만 시작점이 존재한다는 것과 적절한 시작점을 골랐다는 것은 다르다.

### 4.2 새 근거를 실제로 찾았지만 최종 결과에서 탈락

**[SJ-N-040](QUESTION_TRACES.md#sj-n-040): “친척이 기초연금을 대신 신청할 수 있는 범위와 근거는?”**

필요한 근거는 대리 신청을 설명하는 기초연금 조항과, 친족의 범위를 정의하는 민법 조항이다. 그래프는 다음 경로를 실제로 찾았다.

```text
기초연금법 시행규칙 제6조 → REFERENCES → 민법 제777조
```

| 근거 | Hybrid 100개 내 순위 | Graph 내 순위 | 최종 결합 순위 |
|---|---:|---:|---:|
| 기초연금법 제10조 | 10 | 2 | 4 |
| 기초연금법 시행규칙 제6조 | 2 | 4 | 2 |
| 민법 제777조 | 없음 | **5** | **36** |

민법 근거는 Graph 한쪽에서만 점수를 받아 `1/(60+5)=0.01538`이었다. 반면 최종 10위의 주변 조항은 Hybrid 20위·Graph 11위에 모두 있어 두 점수의 합 `0.02658`을 얻었다. **새 근거 발견에는 성공했지만, 두 목록의 중복 출현을 보상하는 결합에서 필요한 정의 조항이 밀렸다.**

[SJ-N-050](QUESTION_TRACES.md#sj-n-050)에서도 휴업사실증명에서 국세청 규정을 거쳐 민원 처리법 시행령까지 2-hop으로 도달했지만, 새 근거는 Graph 13위→결합 27위로 탈락했다. 이번 실행에서 Hybrid 100 밖의 새로운 정답 그룹을 추가한 경우는 이 두 그룹이었고, 둘 다 최종 10개에는 남지 못했다.

### 4.3 연결이 있어도 탐색 정책이 사용하지 않는 경우

**[SJ-A-029](QUESTION_TRACES.md#sj-a-029): “한부모가족증명서를 발급받을 때 신분증 두 종류를 다 가져가야 하나?”**

Hybrid는 ‘택1’을 설명하는 제출서류 근거를 2위에 찾았다. 올바른 서비스도 시작점으로 선택됐고, 그래프에는 `서비스 → REQUIRES → 신분증명서`와 해당 원문 evidence가 있다. 그러나 기본 확장은 `REQUIRES`를 따라가지 않았다. 정답은 Graph 쪽의 보상을 받지 못하고 결합 14위로 밀렸다.

이 사례는 **원문이나 evidence가 없어서 생긴 실패가 아니라, 필요한 관계를 사용하지 않은 실패**다. 추가 수집·바인딩 복구·관계 선택·최종 정렬을 같은 문제로 묶어 고치면 안 되는 이유다.

## 5 왜 개선 가설을 세 가지로 나눴는가

세 가설은 **그래프 검색 과정의 서로 다른 실패 지점**에 대응한다. 여기서 H는 Hypothesis, 즉 검증할 가설을 뜻한다.

```text
H1 시작점을 잘 골랐는가?
      ↓
H2 필요한 근거에 실제로 연결돼 있는가?
      ↓
H3 모은 근거 중 정답을 최종 결과에 남겼는가?
```

시작점을 잘못 고르면 올바른 그래프가 있어도 다른 곳을 탐색한다. 시작점이 맞아도 연결이 없으면 근거를 모으지 못한다. 두 단계가 잘 작동해도 순위가 낮으면 최종 10개에서 빠진다. **어느 단계의 변경이 어떤 효과를 냈는지 알아보기 위해 세 문제를 분리한 것이다.**

| 가설 | 검증하려는 생각 | 이 가설이 필요한 이유 | 바꾸는 것 |
|---|---|---|---|
| **H1 시작점 선택 개선** | 노드 명칭만 맞추기보다 Hybrid가 찾은 원문의 문맥으로 진입하면 필요한 근거에 더 잘 도달한다 | 구어체 질문의 표현과 서비스·조문 이름이 달라 명칭 매칭이 실패할 수 있음 | 시작 노드 선정 방식 |
| **H2 관계·evidence 연결 보완** | 누락된 연결을 복구하면 기존 원문의 필요한 근거가 그래프 후보에 포함된다 | 원문은 corpus에 있어도 명칭·별칭·부정문 처리 때문에 그래프에 제대로 연결되지 않을 수 있음 | 그래프의 보완 대상 연결 |
| **H3 최종 재정렬** | 후보에 이미 있는 정답을 질문과의 관련도로 다시 평가하면 최종 결과에 더 잘 남는다 | 후보 Recall은 높지만 최종 Recall이 낮고, 새 참조 근거도 순위에서 탈락함 | 후보를 최종 정렬하는 방식 |


### 원래 구상과 이번 병합 코드의 차이

| 항목 | Notion의 구상 | 이번에 실제로 검증한 범위 |
|---|---|---|
| H1의 명칭 매칭 | Bigram 기반 시작점과 Hybrid 기반 시작점 비교 | 기존 피드백을 유지해 **Kiwi 명칭 매칭과 Hybrid 기반 시작점**을 비교 |
| H2의 연결 보완 | 누락된 관계·evidence 전반의 보완 | 최신 법령 참조 처리는 유지하고, **검수된 별칭·부정문 3건의 evidence 바인딩**만 전후 비교 |
| H3의 reranker | 같은 후보에서 RRF와 재정렬 비교 | 새 학습 모델 대신 **RRF·청크·인용문의 관련도를 합치는 규칙 기반 재정렬** 사용 |

따라서 이번 H1을 “Bigram보다 Hybrid가 좋았다”, H2를 “모든 법령 연결 누락을 해결했다”, H3를 “학습형 reranker를 검증했다”고 설명하면 실제 실험과 달라진다.

## 6 세 가설을 검증했더니 무엇이 달라졌는가

### 6.1 H1 시작점 선택 개선

**바꾼 것:** Kiwi로 질문과 노드 이름을 맞춰 시작점을 고르는 방식에서, Hybrid 청크의 evidence를 역조회해 시작점을 고르는 방식으로 바꿨다. 두 조건 모두 같은 적격 Service·Article 집합을 사용했다.

**고정한 것:** Hybrid 후보, 그래프, 탐색 관계·예산, Graph 점수식, 최종 RRF를 유지했다. 특히 두 조건의 시작점 가중치를 모두 **1로 고정**했다. 명칭 매칭 점수와 Hybrid 순위 점수의 크기까지 함께 바뀌면 ‘시작점 선택’의 효과를 분리하기 어렵기 때문이다.

| 지표 | Kiwi 명칭 시작점 | Hybrid 기반 시작점 |
|---|---:|---:|
| 완전 회수 질문 | 113/177 | 135/177 |
| Recall@10 | 67.80% | 79.66% |
| Graph 후보의 Recall | 56.87% | 72.88% |
| Hybrid+Graph 전체 후보의 Recall | 97.83% | 98.02% |

**해석:** 회수한 근거 그룹이 늘어난 질문은 34개, 줄어든 질문은 10개다. Hybrid 원문을 통해 진입하는 방식은 명칭 매칭보다 유리했지만 모든 질문에서 좋지는 않았다.

- **개선 [SJ-A-061](QUESTION_TRACES.md#sj-a-061):** 생계급여 통지 기한 조항은 Hybrid 10위였다. 명칭 시작점에서는 Graph 후보가 아니어서 결합 18위였지만, Hybrid 시작점에서는 참조 관계로 연결돼 Graph 8위·결합 7위가 됐다.
- **악화 [SJ-N-020](QUESTION_TRACES.md#sj-n-020):** 지방세 과세증명과 납세증명의 차이를 묻는다. 명칭 방식은 두 서비스의 근거를 결합 5·3위에 올렸지만, Hybrid 방식은 체납 조문 5개로 시작점이 쏠려 정답이36·21위로 밀렸다.

**남은 문제:** 원문 문맥을 쓰는 것은 도움이 되지만, 상위 문서가 한 주제로 쏠리면 시작점도 쏠린다. 서로 다른 서비스·조문을 적절히 남기는 선택이 필요하다.

### 6.2 H2 누락 evidence 연결 보완

**바꾼 것:** 가족관계 등 축약 표기, 토지이용계획확인서/확인원 별칭, 국문 장애인증명의 ‘구비서류 없음’이라는 세 evidence의 바인딩을 보완했다.

**고정한 것:** corpus·질문·검색 설정과 최신 법령 참조 파서를 유지했다. 두 그래프는 노드 6,182개·엣지 9,437개로 같고, evidence record만 11,095→11,098, 서비스 바인딩 6개가 추가됐다. 원문을 새로 수집한 실험이 아니다.

| 지표 | evidence 보완 전 | evidence 보완 후 |
|---|---:|---:|
| 완전 회수 질문 | 130/177 | 132/177 |
| Recall@10 | 76.84% | 77.97% |
| Graph 후보의 Recall | 71.47% | 72.88% |
| Hybrid+Graph 전체 후보의 Recall | 98.02% | 98.02% |

| 보완한 evidence | 실제 변화 | 확인한 효과 |
|---|---|---|
| 가족관계·기본·혼인·입양의 축약 표기 | [SJ-A-080](QUESTION_TRACES.md#sj-a-080), 결합11→1위 | 해당 서비스가 시작점에 포함되고 표의 근거를 회수 |
| 토지이용계획확인원 별칭 | [SJ-B-035](QUESTION_TRACES.md#sj-b-035), 결합15→2위 | 시작점은 그대로이고 수집 가능한 evidence가 늘어남 |
| 국문 증명의 ‘구비서류 없음’ | [SJ-B-038](QUESTION_TRACES.md#sj-b-038), 결합10→1위 | 이미 완전 회수하던 질문이라 성공 수는 같고 순위가 향상 |

**해석:** 두 질문의 완전 회수를 회복했고 회수 그룹 수가 줄어든 질문은 없었다. 다만 **Hybrid와 Graph를 합친 후보 Recall은 98.02%로 그대로**였다. 필요한 원문은 이미 Hybrid 후보에 있었고, 보완 후 Graph에서도 수집·점수 부여가 가능해진 것이다. “새 원문을 더 찾아서 개선됐다”는 결과와 구분한다.

### 6.3 H3 최종 재정렬

**바꾼 것:** RRF 순위만으로 최종 10개를 고르는 대신, 질문과 청크·인용문의 관련도를 함께 반영했다.

```text
재정렬 점수 = 0.5 × 정규화한 RRF 점수
            + 0.3 × 질문과 청크의 Kiwi IDF 관련도
            + 0.2 × 질문과 인용문의 Kiwi IDF 관련도
```

RRF 순위 정보를 남기면서 원문 관련도를 추가한 고정 규칙이다. **0.5·0.3·0.2가 최적이라고 튜닝·검증한 것은 아니며**, 새 Dense 검색이나 학습형 모델을 실행한 것도 아니다.

**고정한 것:** 시작점, 탐색 경로, 재정렬 전 후보 집합과 최종 반환 수 10개를 동일하게 두었다. 후보 자체가 좋아진 효과와 순위만 바꾼 효과를 섞지 않기 위해서다.

| 지표 | RRF 결합 | 규칙 기반 재정렬 |
|---|---:|---:|
| 완전 회수 질문 | 132/177 | 134/177 |
| Recall@10 | 77.97% | 79.28% |
| Hybrid+Graph 전체 후보의 Recall | 98.02% | 98.02% |
| MRR@10 | 0.5579 | 0.5618 |

**해석:** 근거 회수량이 늘어난 질문은 4개, 줄어든 질문은 1개다. 후보 밖에 있던 근거를 새로 찾은 것이 아니라, 이미 후보에 있던 근거 일부를 Top-10으로 올렸다.

- **개선 [SJ-A-002](QUESTION_TRACES.md#sj-a-002):** 만료된 여권을 신분증으로 제시할 수 있는지 묻는 질문에서 ‘유효기간 내 신분증’ 근거가 29→6위로 올라 미발견에서 성공으로 바뀌었다.
- **악화 [SJ-A-035](QUESTION_TRACES.md#sj-a-035):** 사업자등록증명의 ‘구비서류 없음’과 신분 확인을 구분해야 하는 질문에서 정답 제출서류가 8→11위로 밀렸다. ‘신분증·서류’ 표현이 더 많이 겹친 다른 서비스의 제출서류가 대신 들어왔다.

**남은 문제:** 같은 단어가 많이 나오는 문서와 대상 서비스·조건에 맞는 문서를 충분히 구분하지 못한다. Kiwi로 토큰화를 개선해도, 토큰 겹침 중심의 최종 점수에는 이 한계가 남는다.

### 6.4 가설별 개선과 최종 목표 달성을 구분

세 가설은 각각의 비교에서는 개선을 보였다. 그러나 **그 결과를 차례로 누적한 최종 모델을 평가한 것은 아니다.**

| 비교 | 바뀐 요소 | 완전 회수 전→후 |
|---|---|---:|
| H1 | 시작점 가중치 1로 고정, 명칭→Hybrid 기반 선정 | 113→135 |
| H2 | 기본 확장 설정에서 세 evidence 보완 전→후 | 130→132 |
| H3 | 기본 확장의 같은 후보에서 RRF→규칙 재정렬 | 132→134 |

기본 확장은 시작 청크 순위의 역수를 가중치로 사용한다. H1은 시작점 선택만 보기 위해 가중치를 1로 바꿨기 때문에, **H1의 Hybrid 조건135개와 기본 확장132개는 서로 다른 설정**이다. 또한 기본 확장에는 이미 evidence 보완이 들어 있으므로 H2의 ‘보완 후’가 기본 확장과 같다.

가설 검증을 마친 뒤 기존 Hybrid와 다시 놓고 보면 다음과 같다.

| 검색 방식 | 완전 회수 / 177 | Recall@10 | MRR@10 |
|---|---:|---:|---:|
| 기존 Hybrid | 140 | 82.20% | 0.6061 |
| 기본 Hybrid+Graph | 132 | 77.97% | 0.5579 |
| Hybrid 시작점·균등 가중치 조건(H1) | 135 | 79.66% | 0.5606 |
| 기본 확장·규칙 재정렬 조건(H3) | 134 | 79.28% | 0.5618 |

**세 가설이 확장 내부의 문제를 일부 줄였지만, 현재 최선의 확장 조건도 기존 Hybrid를 넘지는 못했다.** 이것이 이번 실험의 최종 판단이다.

## 7 다음에는 무엇을 개선할 것인가

아래는 **이번에 구현·검증한 결과에서 도출한 다음 작업**이다. 현재 성능표에 포함된 방법과 구분한다. 우선순위는 누락 근거 대부분이 후보 안에 있다는 관찰을 따른다.

### 우선순위 1 찾은 근거를 최종 결과에 남기기

**출발점:** N040·N050은 새 참조 근거를 찾고도 밀렸고, A035는 다른 서비스의 공통 표현에 밀렸다.

**다음 비교:** 같은 후보에서 현재 RRF, 현재 규칙 재정렬, 질문과 원문을 함께 읽는 문맥 기반 reranker를 비교한다. 대상 서비스·신청인·발급 채널·연도·부정 조건과 경로의 역할을 함께 고려하는 방식을 검토한다. 기존 Hybrid 상위 근거 보존이나 신뢰할 수 있는 새 참조 근거의 선택 정책도 별도의 실험으로 둔다.

**연구 연결:** [BERT passage reranking](https://arxiv.org/abs/1901.04085)은 첫 검색 뒤 질문과 passage를 함께 평가하는 접근을 제시한다. [RRF 원 논문](https://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf)은 순위 결합 방식의 근거다. 조건부·가중 결합의 효과가 이 프로젝트에서 검증됐다는 의미는 아니다.

**확인할 것:** 완전 회수·Recall·MRR뿐 아니라 **기존 Hybrid 성공을 잃은 질문 수**, 새 정답 그룹이 최종에 남은 수, 다른 서비스 문서의 유입과 추가 지연시간을 함께 본다.

### 우선순위 2 시작점과 탐색 관계를 질문에 맞게 선택하기

**출발점:** N020은 비교 대상 두 서비스 대신 체납 조문으로 시작점이 쏠렸다. A029는 올바른 서비스가 있어도 REQUIRES를 제외했다.

**다음 비교:** Hybrid 바인딩 후보와 Kiwi 서비스 후보를 함께 확보한 뒤 서비스·조문 시작점이 편중되지 않도록 선택한다. 제출서류 질문은 REQUIRES, 기관·처리 질문은 HANDLED_BY, 법적 근거 질문은 GROUNDED_BY·REFERENCES를 사용하는 정책을 따로 검증한다. 평가 데이터의 정답 질문 유형을 검색기에 그대로 전달해서는 안 된다.

**연구 연결:** [BLINK](https://aclanthology.org/2020.emnlp-main.519/)의 후보 검색 후 문맥 재정렬은 시작점 선택의 참고다. [G-Retriever](https://arxiv.org/html/2402.07630v3)와 [RoG](https://arxiv.org/abs/2310.01061)는 필요한 부분그래프·관계 경로를 선택하는 연구 방향을 제시한다. 이 논문 모델들을 현재 구현했다고 주장하지 않는다.

**확인할 것:** 적절한 시작점 포함 여부, Graph 후보의 정답 회수, 최종 회수를 분리한다. 같은 탐색 예산에서 필요한 근거와 무관한 후보가 각각 얼마나 늘었는지 비교한다.

### 우선순위 3 연결이 부족한 고시와 공통 절차 조항 보완하기

**출발점:** [N056](QUESTION_TRACES.md#sj-n-056)의 연도별 고시는 Law 노드의 식별 evidence에만 연결돼 있다. [B010](QUESTION_TRACES.md#sj-b-010)·[B011](QUESTION_TRACES.md#sj-b-011)의 공통 절차 조항은 노드와 근거는 있지만 진입 엣지가 없다.

**다음 작업:** 원문의 적용 범위를 먼저 확인하고, 고시의 대상·연도·수치 기준과 공통 절차 조항을 어떤 서비스에 연결해야 하는지 검수한다. 원문 근거 없이 관계를 추가하지 않는다. 이미 검수한 별칭·부정문 규칙도 출처·표 셀·조건을 함께 보존한다.

**확인할 것:** 연결 추가의 정확성과 실제 도달 가능성, 기존 연결의 회귀 여부를 점검한다. 단순히 노드·엣지 수가 늘어난 것을 성능 개선으로 계산하지 않는다.

### 다음 검증에서 고정할 원칙

- 현재 질문을 보며 정책을 조정한 만큼, [같은 의도 질문 묶음](../../data/intent_groups.jsonl)을 개발·평가 양쪽에 섞지 않는다. 별도의 고정 평가셋에서 결과를 확인한다.
- 한 실험에서는 시작점·관계·가중치·재정렬 중 한 요인을 먼저 바꿔 원인을 분리한다.
- Week4 확장 자체의 0/1/2/3-hop을 비교해 **시작 서비스의 근거 묶음 효과와 관계 이동의 효과**를 구분한다. 기존 Graph 단독의 hop 결과를 확장의 hop 실험으로 대신하지 않는다.

## 8 이번 결과를 어떻게 정리할 수 있는가

**구현 측면에서는** Hybrid 결과를 그래프에 연결하고, 추가 원문을 수집하고, 기존 후보와 결합한 뒤 출처·경로를 남기는 확장이 완성됐다.

**성능 측면에서는** 후보 정답 회수는 소폭 늘었지만 최종 성능은 기존 Hybrid보다 낮았다. 서비스별 근거를 묶는 장점과 실제 참조 경로를 따라 새 근거를 찾는 장점은 확인했으나, 최종 순위 선택과 관계 정책에서 그 이점을 잃었다.

**가설 검증 측면에서는** 시작점 선택·evidence 연결·최종 정렬을 나눠 각각의 기여와 부작용을 확인했다. 다음 단계는 문서를 무조건 더 모으거나 깊게 탐색하는 것보다, **필요한 관계를 사용하고 찾아낸 근거를 최종 결과에 남기는 것**이다.

<summary>평가 한계와 수치 검증</summary>

평가 대상 177질문에 필수 근거 그룹 220개가 있다. 각 그룹은 허용 청크 중 하나를 찾으면 회수로 인정한다. Recall은 질문별 비율의 평균이므로 전체 회수 그룹의 단순 합산 비율과 다르다. 청크 회수 성공은 답변 생성 성공이나 인용문이 정답 명제를 직접 입증했다는 뜻이 아니다. Gold의 전수 사람 검수 상태도 아직 `pending`이다.

저장된 14개 조건의 지표를 다시 계산해 원 지표와 대조했고, 기존 Week3의 7종도 현재 Gold로 재평가해 Top-10 지표가 같음을 확인했다. 직전 실행과 이번 실행의 기존 7종 예측 JSON 내용은 동일하다. 보고서를 고치면서 검색이나 모델을 다시 실행하지 않았다.

Notion에 적힌 과거 기본 비교는139→131개였지만, 이번 병합 실행은140→132개다. **Notion은 설계 의도와 가설 정의의 출처로, 현재 실행 파일은 이번 성능 수치의 출처로 구분했다.** 원문에는 특정 설정값이 최적이라는 검증이나 세 가설을 누적한 최종 실험은 제시되어 있지 않다.
