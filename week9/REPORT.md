# Civic-Link · Week 9 검증 보고서

A는 단일 검색, B는 반복 검색, C는 반복 검색과 Graph를 사용할 수 있는 조건이다. 지정 근거는 벤치마크가 질문마다 정해 둔 필수 근거다. 평가 대상은 608문항 실행 기록, 답변형 488문항의 검색 결과, 60문항 자동 채점, 항목별 추가 실험이며 범위는 항목마다 표시했다.

## 2. 누적 근거와 첫 검색 재정렬

**질문** · 검색할 때마다 쌓이는 근거는 어떻게 보관되고, 후보 100개에는 있지만 최종 10개에서 빠지는 문제는 재정렬로 줄일 수 있는가.

**현재 정책** · 각 검색은 BGE 순위 상위 10개를 반환한다. 본문은 ID별로 누적되고, 추가 탐색 중에는 최신 결과, 종료 예산에 가까워지면 확인 항목에 연결한 근거를 우선해 최대 60,000자 범위에서 전달한다. 답변형 488문항에서 B/C가 확보한 지정 근거의 최종 전달 손실은 0건이었다.

**재정렬 대안** · 첫 검색 실패 53문항 중 47문항은 후보 안 순위 문제, 6문항은 후보 자체 누락이었다. 보존된 후보와 BGE 순위는 그대로 두고, 질문과 본문의 IDF 가중 어휘 일치 순위를 RRF(`k=60`)로 더하는 대안을 비교했다. 순위 결정에 정답은 쓰지 않았고, 488문항의 코퍼스 지문과 BGE 상위 10개가 보존 원본과 일치함을 확인했다.

| 첫 검색 분류 | 문항 | 대안 결과 |
|---|---:|---|
| BGE 상위 10개에서 완전회수 | 435 | 404 유지, 31 퇴보 |
| 후보에는 있으나 상위 10개에서 누락 | 47 | 13 회복, 34 미회복 |
| 후보 자체에서 누락 | 6 | 6 미회복 |

**판단** · 완전회수는 BGE **435/488(89.14%)**, 대안 **417/488(85.45%)**로 18건 줄었다. 전체 재정렬은 기존 BGE를 유지하고, 누적 본문 보존 정책을 바꿀 근거도 나오지 않았다.

## 3. Graph 사용과 역참조

**질문** · Graph를 쓸 수 있는데 성능 개선으로 이어지지 않은 이유는 무엇이고, 보류한 개선 항목과 역참조는 어떻게 되는가.

**사용 현황** · C에서는 608문항 모두에 Graph 후보가 표시됐으나 실제 호출은 13문항 15회(직접 조회 9, 관계 탐색 6)였다. 새 필수 근거가 추가된 호출은 3회다. B→C에서 최종 필수 근거 회수는 5문항 개선·3문항 퇴보였는데, 개선 중 실제로 Graph를 선택한 것은 `SJ-N-050` 한 건이다.

**원인 분석 (C에서 최종 필수 근거가 빠진 28문항)**

① **도달 가능성**: 표시된 후보를 직접 조회하거나 관계 한 홉을 탐색했을 때 빠진 근거가 반환되는지 저장 Graph로 재현했다.

| 측정 | 문항(28) |
|---|---:|
| C가 실제로 Graph를 호출 | 2 |
| 후보 중 하나라도 빠진 근거에 도달 | 25 |
| 후보 직접 조회로 도달 | 19 |
| 현재 나가는 방향 관계 한 홉으로 도달 | 5 |
| 들어오는 방향(역참조)에서만 도달 | 6 |
| 어떤 후보로도 도달 못함 | 3 |

② **Qwen의 선택**(84회): 같은 28문항의 C 첫 입력을 재사용해 허용 행동과 후보 수만 바꾸고, 선택한 요청을 저장 Graph에서 실행해 채점했다. 정답은 모델에 보이지 않았다.

| 조건 | 선택한 행동 | 빠진 근거 확보 | 형식 오류 |
|---|---|---:|---:|
| 원래 허용 행동(검색·Graph·응답) | 응답 21, 검색 6, Graph 0 | - | 1 |
| Graph만 허용 | Graph 28 | 6/28 | 0 |
| Graph만, 후보 앞 8개만 | Graph 28 | 5/28 | 0 |

- **병목은 후보 선택 이전의 판단이다.** Graph가 가능한 상태에서도 0/28이고, 21문항은 근거가 빠졌는데 응답을 택했다. 억지로 Graph를 쓰게 해도 6/28이며, 도달 불가능한 대조 3문항은 전부 0건이었다.
- **"후보가 많아서 못 고른다"는 가설은 뒷받침되지 않았다.** 후보를 8개로 줄여도 6→5였다(후보는 문항당 중앙값 23개, 도달하는 후보는 중앙값 3개). 후보 8개 조건에서 5문항은 문서 후보 ID를 직접 읽었고 그중 4문항이 빠진 근거를 얻었다. 5문항 규모라 가능성 수준이다.
- **역참조**: 도달 경로를 추가하는 문항은 6개이고, Qwen이 고른 요청을 양방향으로 실행해도 새로 확보한 문항은 1건이었다. `SJ-B-034`에서 같은 시작점의 방향만 바꾸면 나가는 방향은 필수 근거 두 묶음 중 하나, 들어오는 방향은 나머지 하나를 반환했고 양방향은 둘 다 반환했다. 이는 시작점을 지정한 도구 수준의 검증이며, Qwen이 방향을 스스로 고르는 효과는 평가하지 않았다. 역참조는 후속 계획의 범위로 둔다.

**이전 주차에 보류한 개선 항목** · `W7-MS-033`은 지정 근거를 모두 확보하지 못해도 답변에 필요한 대체 근거를 읽으면 충분한 사례이고, 재검색으로 처리기간 조문을 확보했다. `W7V2-MS038`은 서로 다른 규정 중 적용 범위를 가를 연결 근거가 필요한 사례이며, C의 추가 검색은 누락 근거를 확보하지 못했다.

**입력 크기** · `W7V2-MS008`은 법령 문서 조회 후 다음 입력이 664,549자로 늘어 모델 호출이 실패했다. 본문 60,000자 제한과 별개로 조문 목록에도 입력 한도를 적용하는 구현 후보가 확인됐다.

**한계** · 분석 대상은 C가 근거를 놓친 28문항이라 "Graph가 쓰이지 않은 이유"를 실패 사례에서 본 것이다. 첫 입력 한 시점의 재생이며 조건마다 한 번 생성했고, 후보 8개 조건은 기존 후보 순서의 앞 8개다. 도달 가능성은 상한값이다(25문항의 첫 검색 후보에는 필요한 청크가 있어 순위 문제와 겹친다).

## 4. Planning 필요성과 효과

**질문** · 처음에 확인 항목을 만드는 과정이 필요한 질문이 얼마나 있고, 기존 문항과 추가 복합 문항에서 효과는 어떻게 다른가.

**문항 구성** · 기존 608문항의 저장된 추론 분류는 직접형 140, 한 단계 이상의 추론이 필요한 유형(한 단계·복수 근거·다단계·인용 연결) 37, 미판정 431개다. 이 분류는 Planning이 도움이 되는 문항 수와 다르고 미판정이 많아, 필요한 규모를 이 분류로는 알 수 없다. 추가 복합 392문항은 두 사람의 문의를 분리해야 하며 답변/답변 312, 답변/확인 질문 40, 답변/보류 40개다.

**실험 흐름**
1. 첫 비교(12문항): 계획을 비우라고 한 조건도 12/12건에서 확인 항목을 반환해 계획 유무를 구분하지 못했다. 이 비교는 효과 판단에 쓰지 않았다.
2. 보정 비교(12문항): 같은 근거로 바로 답변하는 조건과, 별도 계획 호출 후 같은 지침으로 답변하는 조건을 비교했다. 효과가 없었다(기존 6문항 2/6 → 2/6, 복합 6문항 5/6 → 5/6). 표본이 작아 판단하기 어려워 문항을 늘렸다.
3. 38문항 확대: 기존 20문항(12문항 비교에서 쓴 6문항 + 해시 순서로 고른 14문항) + 복합 18문항(답변/확인 질문/보류 각 6개를 해시 순서로 선정), 114개 호출 모두 정상 반환. 변형 이름을 가린 Qwen 루브릭 채점(기대 행동·필수 내용·금지 주장)으로 판정했고, 차이가 난 6문항은 사유를 직접 읽었다.

| 문항군 | 바로 답변 | 계획 전달 | 응답 시간(계획 호출 포함) | 총 토큰(계획 호출 포함) |
|---|---:|---:|---|---|

| 복합 18문항 | 14 | 15 | 7.5초 → 8.5초 | 9.1k → 17.7k |

**38문항 상세** · 통과는 모든 하위 과제(복합 문항은 A와 B 모두)가 기대 행동(답변·확인 질문·보류)과 필수 내용을 충족하고 금지된 주장이 없는 경우다. 복합 문항에는 두 부모 문항의 첫 검색 본문을 합쳐 공급했다. 비용은 계획 호출이 있는 조건에서 계획과 답변의 합계다.

- **개선, 확인 질문이 필요한 문항 3건** · `W7V2-BH002`는 바로 답변이 현재 채널을 묻지 않고 답했고, 계획 조건은 두 경우를 설명한 뒤 채널 확인을 요청했다. `W8-COMP-0332`의 B는 바로 답변이 "졸업증명서일 가능성이 높다"고 추측했고, 계획 조건은 학교급과 학력 형태를 물었다. `W8-COMP-0348`의 B는 바로 답변이 답변으로 끝났고, 계획 조건은 증명서의 발급일·유효기간·단축 사유 확인을 요청했다.
- **개선, 그 외 2건** · `W7-MS-013`은 계획 조건에서 제13조 사후조사와 시행령 제7조제1항의 연결이 담겼고, `SJ-N-028`은 서류명에 더해 조건·예외 구분이 담겼다.

**판단** · 일반 Planning을 공통 단계로 넣을 근거는 약하다(기존 +3, 복합 +1, 비용 약 2배). 효과는 확인 질문이 필요한 문항에 집중되므로, 위 1절의 "빠진 사실 점검" 단계를 후속 후보로 둔다. 복합 392문항 전체에서의 효과는 이 38문항으로 추정할 수 없다. 모두 근거를 고정한 답변 단계 실험이며 복합 질문의 검색 개선 평가와는 범위가 다르다.

## 5. 재질문 이후 상태 유지·재개

**질문** · 사용자에게 추가 정보를 물은 뒤, 앞서 모은 근거와 진행 상태로 이어서 답할 수 있는가. 이를 LangGraph/LangChain으로 구현하면 현재 구조와 무엇이 다르고 전환에는 무엇이 필요한가.

**기존 구조** · 기존 컨트롤러는 확인 질문도 답변(`respond`)의 하나로 보고 그 자리에서 종료한다. 사용자가 답해도 앞서 모은 근거와 진행 상태가 남지 않아 처음부터 다시 시작한다. 이를 질문이 필요하면 질문하고 멈춘 뒤, 사용자의 답을 받아 이어서 다시 답변을 생성하는 구조로 바꿨다.

**재질문 뒤에도 첫 검색 근거로 충분한가** · 벤치마크에서 재질문 뒤 정답 요지와 필요한 근거가 정해진 확인 질문형은 60문항 중 5문항뿐이다(나머지 55문항은 재질문 뒤 정답을 새로 만들지 않았다). 이 5문항에서 사용자가 답한 뒤 필요한 근거를 첫 검색 근거가 이미 담은 경우는 **1/5**(`SJ-N-065`만 포함)였다. 코드로 계산한 값이며, 사용자의 답을 반영한 새 검색이 필요하다는 근거다. 또 Qwen이 만든 사용자 답장이 "모르겠다"인 문항(`SJ-N-066`, `SJ-N-084`)에서는 응답이 일반 설명으로 빠지거나 근거 없는 단정이 나와, 정보를 얻지 못한 경우의 처리가 필요하다.

**재질문 정책과 구현** · 목표는 재질문이 필요한 상황에서 멈추지 않고 이어가는 기능이며, 답변 품질을 높이는 것이 아니다. 정책은 다음과 같이 정했다.

| 항목 | 정책 | 구현 |
|---|---|---|
| 질문 여부 판단 | Qwen이 판단한다. 답변 전 점검 단계에 더해 질문을 선택 가능한 행동(`ask_user`)으로도 제공한다 | 점검 단계(`use_gate`)와 `ask_user` 행동(`allow_ask`)을 각각 끌 수 있다. 질문 지침만 더했을 때 충분한 질문이 0/6이었고 점검 단계로 분리하면 55/60문항이었던 결과에 따라 점검 단계를 유지했다 |
| 답변 횟수 | 사용자의 답은 한 번만 받는다 | 저장소가 첫 답을 원자적으로 수락하고, 두 번째나 동시에 온 답은 거절한다. 재개 뒤에는 `ask_user`를 허용하지 않는다 |
| "모르겠다" | 답변 불가로 처리하고 확인할 방법을 안내한다 | 짧은 "모르겠어요" 답은 모델 호출 없이 "알려 주신 내용만으로는 정확히 안내드리기 어렵습니다. 아래 내용을 확인하신 뒤 다시 문의해 주세요." 와 물었던 질문을 돌려준다(`needs_information`). 긴 답은 응답 지침이 추측하지 않고 같은 안내를 하도록 한다 |
| 호출 한도 | 멈추기 전후를 이어서 센다 | 모델·도구 호출 횟수를 저장된 상태와 함께 복원한다 |
| 만료 | 5분(설정값)이 지나면 이어갈 수 없다 | 만료된 세션은 거절하고 저장된 상태를 삭제한다 |
| 개인정보 | 입력하지 않도록 안내하고, 규칙으로 감지되면 저장하거나 모델에 넘기지 않는다 | 질문과 함께 안내 문구를 보여 주고, 사용자 답과 원래 질문의 주민등록번호·전화번호·카드번호는 마스킹한 뒤에만 사용한다. 모델이 만든 질문이 주민등록번호 등을 요구하면 사용자에게 보이지 않고 거절한다. 사용자 답은 저장하지 않고 완료하면 세션을 삭제한다 |

**구현 구조** · `InteractiveAgent`는 `start()`에서 첫 검색 → 점검 → 질문이 필요하면 `waiting_for_user`로 멈추고 상태를 SQLite에 저장한다. `reply(세션 ID, 답)`은 답을 수락하고 마스킹한 뒤 답을 반영한 검색을 한 번 하고 응답을 생성한다. 기능을 모두 끄면 기존 컨트롤러와 동작이 같다. 저장된 Qwen 응답과 검색 결과를 재생해 608문항 × 3조건 1,823개 실행의 프롬프트와 이벤트가 원본과 모두 일치함을 확인했다. 새 의존성은 없고 기존 컨트롤러를 확장했다.

**검증** · 확인 질문형 60문항에서 점검 단계를 켠 에이전트를 실제 Qwen으로 실행하고, 멈춘 상태를 복사해 같은 상태에서 여러 답을 시험했다. 단위 테스트 41개(대기·재개, 답변 1회, 만료, 마스킹, 모르겠다 판별 등)도 통과했다.

| 시나리오 | 문항 | 결과 |
|---|---:|---|
| 질문하고 멈춤 | 60 | 57문항이 멈춤. 멈추지 않은 3문항은 `W7-BH022`, `W7V2-BH005`, `W7V2-BH007` |
| "모르겠어요" | 57 | `needs_information` 57/57, 추가 모델 호출과 검색 0회 |
| 주민등록번호가 섞인 답 | 57 | 정상 응답 57/57, 번호가 모델 입력·검색어·저장된 세션·이벤트에 남은 경우 0건 |
| 벤치마크에 저장된 사용자 답 | 5 | 응답 5/5, 인용 근거가 재질문 뒤 필요한 근거를 모두 포함한 경우 4/5 |

- 마지막 행의 `SJ-N-084`는 필요한 근거 2개 중 하나를 인용하지 않았다. 정답 근거를 넣어 준 조건이라 구조가 아니라 근거 활용의 한계다.
- **한계**: 재검색은 정답 근거를 돌려주는 대체 검색이라 답변 품질은 상한값이다. 사용자가 실제로 답을 입력하는 화면이나 API는 구현하지 않았고 `reply()`를 호출하는 형태까지만 있다. 마스킹은 형식이 정해진 번호만 잡고 이름이나 주소는 걸러내지 못한다. "모르겠다"를 규칙으로 판별하는 것은 짧은 답(15자 이내)뿐이다. `ask_user`가 실제 실행에서 선택되는 빈도는 측정하지 않았다. 점검 단계의 불필요한 질문(12%)은 그대로다.

**프레임워크 검토** · 같은 기능을 LangGraph로 구현할 수 있는지 프로토타입으로 확인했다(코드는 `feat/langgraph-prototype` 브랜치에 있고 병합하지 않았다). 기존 반복 검색 루프를 노드와 조건 간선으로 옮기되 입력 구성·도구 실행·결과 조립은 기존 메서드를 그대로 썼다.

- **동일성**: 저장된 Qwen 응답과 검색 결과를 재생해 608문항 × 3조건 1,823개 실행의 모델 입력 전체와 이벤트가 기존 루프와 모두 일치했다(모델 오류 1건은 재생할 수 없어 제외, 호출 한도 소진·모델 오류 경로는 단위 테스트로 확인).
- **재개 동작**: 점검 → 멈춤 → 새 연결에서 SQLite 체크포인트로 재개 → 대화 이력 주입 → 새 검색 1회 → 응답이 정답이 있는 5문항에서 모두 동작했다. 재검색은 정답 근거를 돌려주는 대체 검색이라 답변 품질은 해석하지 않는다.

LangGraph와 LangChain은 공식 문서 기준으로 비교했다(LangChain은 실험하지 않았다).

| 방식 | 재개 동작 | 전환 시 필요한 작업 |
|---|---|---|
| 현재 컨트롤러 확장 | 물어볼 필드와 근거 상태를 저장하고, 후속 입력에서 세션 ID로 복원 | 상태 직렬화, 세션 저장소, 원자적 갱신, 검색·모델 호출 한도, API의 대기/완료 응답 정의 |
| LangGraph | checkpointer로 상태를 보관하고 `thread_id`, `Command(resume=...)`로 재개 | 현재 루프를 노드로 옮기고 검증·도구 캐시·호출 한도·이력 형식을 재연결. 재개 시 중단 노드가 처음부터 실행되므로 외부 호출 위치를 정해야 함 |
| LangChain | 에이전트의 단기 메모리를 checkpointer와 스레드에 연결 | 메시지와 상태는 보관 가능. 근거 제한, Graph 커서, 재개 분기, A/B/C 실험 규칙은 별도 이식 |

**판단** · 재질문 기능은 기존 컨트롤러를 확장해 구현했다. 상태 저장만으로는 재질문 뒤 필요한 근거가 부족한 경우가 많아(1/5), 재질문 답을 반영한 재검색 단계를 재개 흐름에 넣었다. LangGraph는 기존 동작을 그대로 옮길 수 있고 멈춤·재개를 체크포인터로 처리할 수 있어, 상태 저장·재개를 직접 구현하는 부담을 줄이는 구조상의 이점이 있다. 답변 품질 면의 이점은 아직 검증하지 못했고, 적용은 실제 검색 환경에서의 재검증과 함께 단계적으로 진행한다.

## 6. 성공·실패군의 개선과 비용

## 결론

이번 검증에서 확인한 것은 **현재 시스템의 병목이 근거를 찾는 단계가 아니라 찾은 근거가 충분한지 판단하는 단계**라는 점이다.

1. **근거 확보보다 판단이 문제다.** 필수 근거는 첫 검색에서 435/488문항이 확보됐고, 반복 검색은 B 458·C 460까지 늘렸다. 반면 근거가 부족한데 응답한 호출이 B 30·C 27건, 근거가 충분한데 도구를 선택한 호출이 B 47·C 80건이다.
2. **근거 보관과 재정렬은 현행을 유지한다.** 누적 근거의 최종 전달 손실은 0건이었고, 어휘 일치 재정렬은 435에서 417로 오히려 줄었다.
3. **Graph가 쓰이지 않은 이유도 같은 판단 문제다.** 빠진 근거에 닿는 후보는 28문항 중 25문항에 있었지만 Graph 선택은 0/28이었고, 억지로 쓰게 해도 6/28이었다. 역참조는 6문항에서만 새 경로를 추가했고 Qwen이 고른 요청에서는 1건이었다.
4. **Planning보다 "빠진 사실 점검"이 맞는 형태다.** 별도 계획 호출은 토큰이 약 2배이고 효과는 확인 질문이 필요한 유형(복합 2→4)에 집중됐다. 이를 점검 단계로 좁히자 확인 질문형 60문항 중 55문항이 질문했고 48문항이 정답 슬롯을 물었다(조정에 쓰지 않은 54문항에서는 44문항). 불필요한 질문(12%)은 보완이 필요하고, 개인정보 요구는 규칙 검사로 막았다.
5. **재질문 뒤에는 새 검색이 필요하다.** 사용자가 답한 뒤 필요한 근거를 첫 검색 근거가 이미 담은 경우는 1/5였다. 기존 컨트롤러를 확장해 대기·재개와 재질문 정책을 구현했고, 확인 질문형 60문항에서 의도대로 작동했다(멈춤 57문항, "모르겠다" 처리 57/57, 개인정보 유출 0건). LangGraph로 옮겨도 기존 동작과 1,823/1,823개 실행에서 일치하고 멈춤·재개가 동작했다.
6. **비용은 실패군에서 커지며 단순 규칙으로는 줄지 않는다.** 순위 탈락 문항의 응답 시간은 B 기준 38.6초에서 55.2초로 늘었고, 같은 요청 반복 차단은 C의 모델 호출을 6.5% 줄이는 데 그쳤다.

따라서 개선 순서는 **근거 충분 여부 판단 → 확인 질문 점검 → 재질문 뒤 재검색**이다. 앞의 둘은 Graph 활용과 비용과도 연결된 문제로 보이나 이 연결은 아직 검증하지 않았다. 다만 재질문 뒤 검증은 정답 근거를 돌려주는 대체 검색으로 했고, 확인 질문과 Planning 결과는 소규모 표본과 Qwen 판정에 기대고 있어 실제 검색 환경과 더 큰 표본에서 다시 확인해야 한다.

## 후속 과제

- **재질문 뒤 재검색**: 실제 검색 환경에서 사용자 답을 반영한 재검색을 검증하고, 이를 바탕으로 LangGraph 적용을 단계적으로 진행한다.
- **비용 절감**: 같은 요청 반복 차단(손실 0건, C 호출 6.5% 절감)을 적용해 재실행하고, 순위 탈락 문항의 반복 검색을 줄이는 방법을 시험한다.
- **확인 질문 점검**: 불필요한 질문(12%)을 줄이며, 복합 문항의 확인 질문 40개를 검증하고, 재질문 뒤 정답이 없는 55문항의 평가 기준을 마련한다.
- **재질문 기능 연결**: 사용자 입력 채널(화면·API)에 `reply()`를 연결하고, `ask_user` 행동의 선택 빈도를 측정한다.
- **근거 충분 판단**: Graph와 추가 검색이 선택되지 않는 직접 원인인 판단 단계를 개선한다.
